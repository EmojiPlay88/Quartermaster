# Piece 4 — Undo and Step Back Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Undo/Redo of the last action and Step Back to any phase checkpoint, by truncating the command log and replaying it from a stored genesis state; save format 5 carries that genesis; autosave keeps 20 + one per turn.

**Architecture:**
- **Core** `GameSession` gains history: a genesis clone, action marks (one per user gesture), checkpoints (phase/turn boundaries), an in-memory snapshot cache, `RewindTo`/`Undo`/`Redo`, a rewind preview, and a new logged command `SteppedBack`. No command gets an inverse; rewinding = replay from the nearest cached snapshot.
- **Core** `NativeSave` format 5 stores genesis, action marks and checkpoints, checks that genesis + log replays to the snapshot, and falls back to "undo starts here" (rebase) on old or inconsistent saves.
- **Render** `HistoryController` orchestrates (reseed + reconcile after a rewind, the `SteppedBack` log line, checkpoint rows with stage/side text, plain-words summary). Existing multi-command gestures in Render get action scopes.
- **App** stays thin: Edit menu, toolbar buttons, Step Back dialog and confirmation, action scopes at App call sites, refresh on rewind, forced autosave before a step back.

**Tech Stack:** .NET 10, C#, WinForms, xUnit (existing).

**Spec:** `docs/superpowers/specs/2026-11-07-piece4-undo-design.md` (binding). Background: master spec `docs/superpowers/specs/2026-11-06-quartermaster-engine-design.md` §2 (content boundary), §5, §9.5. Earlier rulings: `docs/superpowers/piece1-followups.md`.

## Global Constraints

- **Content boundary (hard):** no game content anywhere. Tests use the existing invented fixtures (`PhaseFixture`, synthetic modules) and invented phase names. The builder never edits the user's TEST pack.
- **Never crash on bad user data:** malformed or tampered saves, dangling ids, rewinds past deleted phases give a message, log line or diagnostic, never an exception reaching the user. UI handlers are guarded (`Guard(...)`).
- **Commands:** every game-state change still goes through `GameSession.Execute`. The reducer stays pure and deterministic. `At`/`Who` are stamped by the issuer (`CommandLog.Stamp`/`Prepare` in App, the injected `prepare` in Render).
- **Undo never drifts:** a rewound state must be JSON-identical (`JsonSerializer.Serialize(state, QuartermasterJson.Options)`) to the state recorded at that log index during play.
- **Formats:** `NativeSave.FormatVersion = 5`; formats 1–4 still load (with the undo floor at the load point).
- **Exact UI copy:**
  - Menu `&Edit` between File and View: `&Undo {label}` / `&Undo` (disabled), `&Redo {label}` / `&Redo` (disabled), `Step &Back to Start of Phase`, `Step Back &To...`
  - Toolbar captions `Undo`, `Redo`, `◀ Step Back`
  - Log line: `Stepped back to {target}. Undid {N} action(s), {D} dice roll(s).` — `{target}` is `Turn 3 · Axis Supply` (U+00B7) or `game start`; the `, {D} dice roll(s)` part is omitted when D = 0. Pluralise properly ("1 action", "2 actions").
  - Summary note on dice: `Rolling again will give new results.`
  - Floor tooltip: `Undo stops here: this game was loaded from a save without undo history.`
  - Confirmation buttons: `Step Back` / `Cancel`
- **Command ids / defaults:** `edit.undo` Ctrl+Z, `edit.redo` Ctrl+Y, `edit.redoAlt` Ctrl+Shift+Z, `phase.stepBack` Ctrl+Left, `phase.stepBackTo` (no default). Toolbar ids `edit.undo`, `edit.redo`, `phase.stepBack`, listed in `ToolbarIds.All` just before `turn.next`.
- **Performance target (spec §10):** Undo < 100 ms, Step Back < 1 s on ~1,200 pieces / ~5,000 commands on the user's machine. Tests assert looser bounds (§Task 8).
- **Build:** `TreatWarningsAsErrors` is on; build must be warning-free. `dotnet test Quartermaster.slnx` green at the end of every task.
- **Test isolation:** tests and smokes never touch the real `%LOCALAPPDATA%`. Smokes run with `QUARTERMASTER_LAYOUT_ROOT=<scratch>/qmroot`; screenshots go to the scratchpad only.
- **Look:** Windows-classic look of pieces 1–3 (Tahoma 8.25pt, system colours, DPI-aware). The Step Back dialog is a modal dialog in the style of `NextPhaseDialog`.
- **Commits:** every commit message ends with a blank line, then `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Repo-local noreply identity only; never stage `startapp.cmd`.

## Review Focus

1. **Undo while a formula dialog, batch grid or missing-input dialog is open.** The windows close, and a stale Apply (its run undone) is refused, never written to the ledger. Task 5 test `ApplyFormula_AfterRunUndone_ReturnsFalse`; Task 7 wires the close.
2. **Ctrl+Z while typing** in a ledger cell, note or formula box: the text box's own undo runs, the game's does not. Task 7 test `ShortcutGate_CtrlZ_InTextControl_NotDispatched`.
3. **Rules pack edited between playing and undoing** (current phase deleted, a new seeded ledger property added). After the rewind the game reconciles with a logged reason and the new key is seeded. Task 5 tests `StepBack_AfterPhaseDeleted_Reconciles` and `Undo_ReseedsKeysAddedSince`.
4. **Old, tampered or hand-edited saves** (format 4, a log entry removed, an action mark pointing past the log). They load, undo starts at the load point, and a diagnostic says why. Task 3 tests.
5. **Autosave fired from inside a gesture** (the phase-boundary autosave during Next Phase). The written save must contain the finished action and its checkpoint, and load with full undo. Task 5 test `PhaseBoundary_RaisedAfterActionClosed`.

### Task 1: Core history — genesis, actions, rewind, undo, redo

**Files:**
- Create: `src/Quartermaster.Core/GameHistory.cs`

**Interfaces:**
- Produces (in `GameHistory.cs`):
  - `public sealed record ActionMark(int Start, string Label);` — `Start` = log index of the action's first command.
  - `public sealed record UndoneAction(string Label, IReadOnlyList<GameCommand> Commands);`
  - `public static class ActionLabels { public static string For(GameCommand first, int commandCount); }`
- Produces (on `GameSession`):
  - `public GameState State { get; private set; }` (was get-only; the object is **replaced** on rewind)
  - `public GameState Genesis { get; private set; }` — deep clone taken in the constructor.
  - `public IReadOnlyList<ActionMark> Actions { get; }`
  - `public IDisposable BeginAction(string? label = null)` — nested scopes join the outermost; the action is created lazily at its first command; a scope that executes nothing creates nothing.
  - `public bool CanUndo { get; }`, `public bool CanRedo { get; }`, `public string? UndoLabel { get; }`, `public string? RedoLabel { get; }`
  - `public IReadOnlyList<UndoneAction> RewindTo(int logIndex)` — truncates to `logIndex` (0 ≤ logIndex ≤ Log.Count), pushes the removed actions on the redo stack so the earliest is redone first, returns them in log order.
  - `public void Undo()` = `RewindTo(Actions[^1].Start)`; `public void Redo()` — re-executes the top redo action under `BeginAction(label)` without clearing the rest of the redo stack.
  - `public void Rebase()` — `Genesis = State.DeepClone()`; clears log, actions, redo, snapshot cache.
  - `public event Action? Rewound;` — raised after every `RewindTo`/`Undo`; `Redo` raises `Changed` per command as usual.
  - `public static bool IsFolding(GameCommand c)` — `SetStackExpanded`, `SeedLedger` (and `SteppedBack` from Task 2).
  - `internal void RestoreHistory(GameState genesis, IEnumerable<ActionMark> actions)` — used by Task 3.

Rules for `Execute(c)`:
- Inside a scope: belongs to the scope's action.
- Outside a scope, folding: joins the last action if any; with no action yet it is an orphan at the head (part of no action, never undone by Undo).
- Outside a scope, not folding: its own one-command action labelled `ActionLabels.For(c, 1)`.
- Creating any action clears the redo stack, except while `Redo` is running.

Snapshot cache: `Dictionary<int, GameState>` keyed by log index, genesis at 0; rewind = clone the nearest cached snapshot ≤ target and `Apply` the commands up to the target. Keep at most 40 entries besides genesis (evict the oldest). Task 2 adds entries at checkpoints; Task 1 caches only genesis.

`ActionLabels.For` defaults (wording is the builder's; these are the starting point): `MovePieces` → `move of {name}` from `LogText` before " moved" when present, else `move of N pieces`; `RollDice` → `roll {Purpose}`; `LedgerDelta` → `{PropertyId} change`; `AdvancePhase` → `Next Phase`; `AddPiece` → `add piece`; `RemovePiece` → `remove piece`; `SetNotes` → `notes edit`; `SetTurn` → `turn change`; anything else → the type name split into words, lower case. Labels from `BeginAction(label)` win.
